The problem

Your AI agent just refunded a customer twice.

Agents are starting to send emails, issue refunds and change production systems on their own. When one crashes halfway through a job, or decides it's "done" when it isn't, real people pay for it. Blackout makes every real-world action happen once, wherever your system can answer "did this already happen?", and lets only code decide the job is done. When it can't tell, it escalates instead of guessing.

▶ See it handle a crash Use it today: MCP gateway GitHub

How it goes wrong

One crash, one second, one very unhappy customer.

This isn't an exotic failure. It's what happens to any worker that is killed between doing something and writing down that it did it. (An illustration. The live demo below uses a simulated notification sender.)

  1. 1:59:58
    The agent issues refund #4417. The payment goes through.
  2. 1:59:58
    The agent's process dies a moment later, before it records "refund sent". A deploy, an out-of-memory kill, a timeout.
  3. 2:00:30
    A fresh agent takes over. Its records say refund #4417 is still pending.
  4. 2:00:31
    It sends the refund again. Then reports "all done", because as far as it can tell, it is.

They double-act

A restarted agent can't tell "didn't happen" from "happened, but nobody wrote it down". Retrying feels safe. It isn't.

They say "done" when it isn't

Health checks stay green while real work fails. Agents grade their own homework, and they grade generously.

Nobody can walk away

Without a clear definition of finished and a budget, agents loop, drift and burn money overnight.

How it works

Three rules, enforced in code.

No new agent framework. Blackout wraps the actions that touch the outside world and holds the agent to a goal it can't quietly lower.

01

Define done first, then freeze it.

The model proposes a definition of done from a fixed vocabulary of checks. Blackout adds the checks it is not allowed to skip, hashes the contract and stores it where no agent can touch it.

02

Write it down before you do it.

Every side effect gets a stable operation ID in a durable journal before it happens. If the worker dies, its replacement asks the outside system for that exact receipt instead of guessing. Unknown outcomes are escalated, never retried blindly.

03

Only code says done.

A deterministic verifier, with no LLM, checks the real system against the frozen contract. Agent claims of success are ignored unless it agrees. No progress means replan, then escalate to a human with evidence.

Use it today · MCP gateway

Put Blackout between your agent and its tools.

The Blackout MCP gateway works with any agent that calls tools over MCP. Your agent doesn't change: point it at the gateway instead of the tool server, and mark which tools have side effects.

# Try it in Claude Code (bundled demo mailer, no setup)
$ npx -y blackout-mcp init
$ claude mcp add blackout -- npx -y blackout-mcp --config "$PWD/blackout.mcp.json"
# then ask Claude to send the same email twice: the second comes back "duplicate suppressed"
// blackout.mcp.json, in front of your own MCP server
{
  "mission": "order-shipped-backlog",
  "downstream": { "command": "node", "args": ["your-mcp-server.js"] },
  "sideEffects": {
    "send_email": { "idempotencyArg": "idempotency_key",
                    "receipt": { "tool": "get_receipt", "arg": "idempotency_key" } }
  }
}

$ npx -y blackout-mcp --config blackout.mcp.json   # a stdio MCP server; add it to any agent

Repeats are suppressed

Every side effect gets a stable ID and is journaled before it runs. A retry or a restarted agent gets the original result back, not a second email.

Crashes are reconciled

If the gateway dies mid-call, it asks your system's receipt tool what happened before allowing a retry. If it can't tell, it refuses and escalates.

Measured live

A Nemotron agent on Crusoe sent 3 emails through the gateway, was restarted with no memory and given the same job. All 3 repeats suppressed; each customer got exactly one email.

The gateway handles exactly-once side effects. "Code decides done" (frozen contract plus verifier) is the full Blackout runtime shown in the race above. Works with anything that can answer "did operation X happen?" by an ID you choose: Stripe idempotency keys, SQS FIFO dedup IDs, a Postgres outbox.

Built on Crusoe + NVIDIA Nemotron

Verification only works if it's cheap enough to always run.

Every Blackout mission is two Nemotron agents making about 28 calls: writing the contract, diagnosing, repairing, deciding. On Crusoe Managed Inference that costs about half a cent, so checking everything is the default, not a luxury.

We picked the model by measuring, not by name. On the same crash mission, Nemotron 3.5 Lightning finished in the fewest turns, Nemotron 3 Super also finished at about six times the cost, and Nemotron 3 Nano did not make progress. Lightning drives all 40 measured missions in the results table. When capacity was tight during the event, Blackout rerouted to Nemotron 3 Super and kept going. In the recorded race above, 26 of Blackout's 27 calls ran on Lightning.
