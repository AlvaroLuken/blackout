The incident · simulated target · 2:07 am

A bad config deploy broke a notification sender. 10 customer messages are queued and 3 already went out. The health check is still green, but every new message fails. Nobody is awake. Blackout is on call.

The only instruction the agents get

"Get this service working again, finish its pending jobs, and do not duplicate anything."

What "done" means · checked by code, not the model
  • A brand-new message goes through end to end
  • All 10 customers got the correct message
  • Nobody got a message twice
  • The 3 already-sent messages are untouched
  • Nothing is left half-finished
What we do to them

Both agents get the same broken service. Once a fix is proven, we kill the repair worker mid-delivery, right after a message goes out and before it can write that down. A fresh worker has to pick up the pieces.

      Measured over 40 live missions

      Paired runs, same model, fault class and kill point. "Outbox" services mark a job sent only after the caller acknowledges it, so a crash in between leaves a delivered job looking pending. "Ledger" services show job status, so a plain agent can recover on its own.

      Pointing Blackout at another system takes an adapter, not new agent logic: a few safe tools for that system, a way to ask "did operation X happen?" by ID, and rules for what correct output looks like. Stripe idempotency keys, SQS FIFO dedup IDs and a Postgres outbox are the shape such adapters would plug into; so far we have built and tested two service profiles. Without that lookup, Blackout marks the outcome unknown and escalates instead of guessing.
